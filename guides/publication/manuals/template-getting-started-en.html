1. Framework and domain selection

The landing page shows Templates, login and the version badge. Members have a visual sample-card SmartList and ordinary chat. The avatar menu retains the small profile and image editor, API access and minimal settings. Notifications, guides, help documents and consent remain available. The administrator shell has no product navigation; administrator API access remains. Operator configuration, email, TLS and update surfaces are retained.

Chat includes message editing, deletion, replies, reactions, pins, read state, reconnect and two-party audio/video calls. It excludes MyScoutee invitations, reports, feedback and support-case management. Calls use encrypted WebRTC media and STUN discovery. A local fake-camera test does not prove physical devices, public-network traversal or a TURN relay.

There is no event, community/group, matchmaking, payment or virtual-company Registry implementation. Necessary account and chat model fields retain their original meaning. Optional product fields are omitted from JSON rather than recreated as empty product domains. Localization and geographic location are both retained.

Architecture and design decisions

Reuse without duplicate business logic. Domain implementations live in the canonical Java source. The assembly selects deployment owners; cross-owner operations use typed transport contracts. Frontend services select local or HTTP repositories while retaining the existing stores and components.

Keep identity boundaries explicit. REAL and DEMO select separate persistent data in normal deployments. The disposable E2E stack deliberately uses its isolated database for both. Local IndexedDB is a browser sandbox; it does not provide server authorization or live calls.

Persist work that must survive restart. Outboxes, account deletion and update jobs retain their progress and retry state. Redis carries live events/cache coordination; MongoDB stores application state, and MinIO stores media. Shared storage in the KVM lab is a deliberate operational simplification, not independent databases per service.

Keep extension points in their existing owners. Add a domain through its contracts, repository and service; extend the shared form, menu or SmartList model for presentation. The Components Guide covers the available controls and providers.

2. Checkout and frontend ownership

The backend is the parent repository. Its frontend submodule is pinned to myscoutee-template-frontend. Run the Git commands below after cloning the parent to initialize the recorded frontend commit. Shared components are installed from the frontend lockfile as an npm dependency.

Commit and push frontend changes to its own repository first, then commit the updated gitlink in the parent. Commit or preserve existing frontend changes before updating its checkout. The frontend submodule uses an ordinary GitHub repository URL.

git clone https://github.com/fssrepository/myscoutee-template.git
cd myscoutee-template
git submodule sync -- frontend
git submodule update --init --recursive --checkout -- frontend
cp server/.env.example server/.env
npm --prefix frontend ci

Use the checked-in Gradle wrapper and frontend lockfile. The development environment uses Java 25, Node 24, Docker Compose and a supported Chrome/Chromium. Install frontend dependencies with npm ci in frontend after initializing the frontend. Never copy local credentials, generated databases or build caches into Git.

3. Local and HTTP development

Browser-local mode uses IndexedDB and the selected four-person seed. In frontend, run npm run start:local and open http://127.0.0.1:4200. It is a UI/data-adapter environment, not a backend or live WebRTC deployment.

HTTP development uses the versioned server/docker-compose-dev.yml and server/docker-dev.env. Its existing backend hot-deploy and frontend synchronization process own compilation and asset delivery. Inspect that process and its logs before starting a build. Do not start another watcher or compile the same target alongside it.

From the parent repository, start or stop the HTTP development composition with its own environment file. These commands create/start containers or stop them; they retain volumes. Initial image preparation follows the same serial build discipline.

docker compose --env-file server/docker-dev.env \
  -f server/docker-compose-dev.yml up -d

docker compose --env-file server/docker-dev.env \
  -f server/docker-compose-dev.yml logs --tail=100 frontend-sync profilemanagement

docker compose --env-file server/docker-dev.env \
  -f server/docker-compose-dev.yml stop

On a constrained workstation, invoke the existing frontend runner directly to cap workers, instead of the convenience script's 12-worker default. Start it only after stopping any compiler for the same target:

cd frontend
NG_BUILD_MAX_WORKERS=2 NODE_OPTIONS=--max-old-space-size=3072 \
  node scripts/with-components.mjs serve --configuration local

The frontend keeps distinct local, dev, E2E, production and GitHub Pages configurations. Production output belongs to frontend/prod; Pages output belongs to frontend/docs. Frontend synchronization, runtime availability and build stamping remain part of the workflow. Preserve relative assets and the configured base path when changing the application name.

Stop the active dev stack before starting KVM, E2E or another application stack. A monolith and the independent-service lab are alternate deployments, not parallel development servers.

4. Automated qualification

../myscoutee-microservices/tools/run-backend-junit.sh standard runs the selected Java unit tests with isolated outputs. Use its --tests filter for a focused change; embedded Mongo checks use the separate embedded group. Frontend tests use npm test -- --watch=false. Do not rerun every suite after each small edit.

tests/e2e/README.md defines the disposable E2E composition, certificate trust, fixture variables and serial runners. Run node tests/e2e/functional/backend/run.mjs for the retained API contracts and node tests/e2e/functional/ui/run.mjs --fail-fast for browser flows. --case selects one matching flow. Each fixture owns its actors and removes them afterward; it must not reset production data or another user's sessions.

Record actual build revisions, image IDs, environment and fixture scope. Browser-local success does not qualify HTTP, and a healthy container does not prove a working user flow. Compare CPU and latency using identical workloads and limits after a coherent change batch. The seven-case read workload has a six-user, 60-second baseline and repeat with zero errors. Throughput was 112.84 and 114.92 completed collection cases/second; p95 was 62.69 and 58.34 ms. These are repeatability results, not an improvement claim against MyScoutee. The delivery evidence also records the completed bounded browser/WebSocket stress selection; it is not a capacity guarantee for an arbitrary deployment.

export E2E_NATIVE_DEMO_SESSIONS=true E2E_SKIP_E2E_RESET=true
export E2E_STRESS_BASE_URL=https://localhost
export NODE_EXTRA_CA_CERTS=/path/to/local-ca.pem
node tests/e2e/stress/backend/run.mjs --scenario template-read --duration-ms 15000
node tests/e2e/stress/backend/run.mjs --scenario template-read --record

See tests/e2e/stress/README.md for matched comparisons and the separate KVM CPU measurements.

5. KVM and monitoring

The template owns a separate VM named myscoutee-template, with four vCPUs and 6 GiB RAM. Its private keys, disks and Terraform state live outside Git under ~/.local/state/myscoutee-template/microservices. Host-boot autostart is disabled. The namespace contains four JVM owners:

OwnerSelected domains
identityAccounts, access, minimal administration, platform, integrations and showcase
communicationChat, notifications, email and localization
mediaMedia storage and processing
helpHelp, guide and consent documents

The lab includes a two-member Mongo replica set with distinct REAL and DEMO databases, Redis, MinIO, MCP, STUN, ingress and a local release simulator. Two voting Mongo members require both for majority writes; this is not one-node-loss availability.

microservices/tools/lab.sh preflight
microservices/tools/lab.sh build
microservices/tools/lab.sh frontend-image
python3 microservices/tools/workloads.py lock-images
python3 microservices/tools/vm.py start
python3 microservices/tools/workloads.py backends-stop
python3 microservices/tools/workloads.py up
python3 microservices/tools/workloads.py forward
microservices/tools/lab.sh monitoring-up

Build support images when their canonical sources change using lab.sh support-images, minio-image and release-simulator-image. Startup imports locked artifacts without rebuilding. Stop backends before deploying changed writers. Helm mounts the canonical Mongo init scripts and REAL/DEMO seed directories as a native read-only image volume. This data-only OCI artifact uses the existing build, lock and registry/cache delivery; no container runs from it. The standard Mongo entrypoint initializes empty database storage, as in Compose. E2E fixtures are excluded and existing database data is preserved. There is no host directory, separate import job or copying init container.

The application is at http://localhost:18080, Grafana at http://localhost:13000, and Prometheus at http://localhost:19090. The loopback-only Grafana login is lab / template-local-only. Use microservices/tools/open-terminals.sh for the live status view or python3 microservices/tools/vm.py observe --once for one snapshot. The terminal shows guest/container CPU, RAM, readiness and host monitoring. Closing it does not stop the VM.

microservices/tools/lab.sh monitoring-stop
python3 microservices/tools/vm.py stop

These commands retain owned data and do not enable autostart. Use the versioned ownership-checked destroy tools only when intentionally discarding a lab; never use global Docker prune as a cleanup substitute.

6. Data and account lifecycle

Canonical Mongo collection/index definitions, selected system catalogs and small demo fixtures are under server/docker/conf/mongodb. Production identity records are empty. The operator provisions real credentials and branding after installation. Browser-local seeds use the same selected model meanings.

Seed import is owned by the existing Mongo/MinIO startup importers and the development seed synchronizer. Preserve runtime-owned users, sessions, configuration and media; do not replace those collections with a demo export. The source parity check is read-only:

npm --prefix config/packaging run seed-parity
python3 ../myscoutee-microservices/tools/check-public.py

The second command checks the already-running owned KVM application. The older seed-mongo.py reset/verification modes apply only to explicitly reviewed recovery of installations carrying its bootstrap marker; they are not required for normal startup.

Account deletion keeps the original grace period, normally 30 days, followed by durable purge retries across the retained owners. Notification outbox delivery, scheduled messages, warning email and integration callback work retain their own state and retry behavior. A removed administrator screen is not a reason to remove necessary lifecycle jobs.

Keep REAL and DEMO boundaries intact in HTTP, internal transport, workers and sockets. Internal actor grants are short-lived and validated per operation. A persistent split-service socket renews through its original account session; message bursts reuse its current grant. Never replace session checks with a caller-supplied user ID.

7. Build another application

Start with the showcase owner and its visual cards. Replace those sample records and presentations with your domain while keeping identity, navigation, popup behavior, SmartList views and chat infrastructure. Add optional JSON fields only when the new application needs them.

Canonical Java implementations remain in server/projects/profile. Add a domain's contracts and implementation there, then select its owner in microservices/assemblies.json. Cross-owner calls use the existing typed transport and authority protocol. Do not copy the monolith into each service.

Frontend contracts, services and repositories follow domain folders across base, HTTP and local adapters. Extend the existing component/store/repository owner, preserving observable local/HTTP behavior. Shared visual controls belong to the existing components submodule. config/upstream-sources.json records the source revisions and deliberate adaptations needed for future upgrades.

8. Installed operation and releases

The Debian package is myscoutee-template, version 1.4.0. It contains the five managed images, selected system/demo seeds, systemd units and common host helpers. MongoDB, Redis and STUN use the pinned upstream images. Package files live under /opt/myscoutee-template, deployment configuration under /etc/myscoutee-template, state under /var/lib/myscoutee-template, and backups under /var/backups/myscoutee-template.

The shared installer generates fresh MongoDB/MinIO credentials, an encryption master key and a deployment-local Operator login. Existing credentials, keys and manual TLS files are preserved. Firebase starts disabled; enabling it requires the deployment service-account file selected by Compose. The installer never creates a Registry identity or imports payment configuration.

The installed VMware qualification covers fresh installation, operator access, TLS, host controls, backup/restore and data-preserving removal/reinstallation. The signed updater was exercised for rejection, interrupted download, retry and recovery. These results apply to the hashes recorded in the qualification evidence. The published UI refresh was compiled and its package contents, image identities and signatures checked separately.

Verify and install

Download the DEB, client-tools archive, signed release manifest, myscoutee-update.json, public key and checksums from the versioned GitHub release. Do not mix assets from different builds. Unpack the client tools, copy install.env.example to a private install.env, and set the local VMware address plus release-verification paths. Keep ALLOW_UNSIGNED_LOCAL_PACKAGE=false.

chmod 0600 install.env
./verify-release.sh ./myscoutee-template_1.4.0_amd64.deb \
  ./myscoutee-template-release_1.4.0.json ./release-public.pem \
  sha256:74255e852bf3720b81b990d0568f5b567124d6fb12335063f0309ccb522c5c03
./install.sh ./myscoutee-template_1.4.0_amd64.deb

Confirm the complete fingerprint through an independent trusted channel; a public key downloaded beside an artifact does not establish its authenticity. The current release authority is for this template distribution. A derived project must establish its own release signing key.

The client invokes package-owned host qualification. Check public transport separately from the client machine:

NODE_EXTRA_CA_CERTS=/path/to/local-ca.pem node verify-deployment/run.mjs \
  --url https://your-local-vm --expected-version 1.4.0 --demo-session

Operate and recover

sudo systemctl start myscoutee-template.service
sudo /opt/myscoutee-template/packaging/scripts/status-production.sh
sudo /opt/myscoutee-template/packaging/scripts/qualify-deployment.sh check \
  --expected-version 1.4.0
sudo systemctl stop myscoutee-template.service

TLS requests and renewal use the retained privileged worker and systemd units. Configure the public URL, certificate and Firebase provider through the existing Operator/deployment workflow. The initial localhost certificate is for bootstrap, not public certificate-chain qualification.

sudo env MONGO_DATABASE=production_db MYSCOUTEE_BACKUP_REQUIRE_COMPLETE=true \
  /opt/myscoutee-template/packaging/scripts/backup-production.sh

A complete backup contains MongoDB, configuration, the matching configuration encryption key and MinIO media. It contains secrets and remains mode 0600. Test restoration on the disposable VMware deployment before relying on it. Restore is explicitly destructive and requires the matching database/key pair:

sudo env CONFIRM_RESTORE=true MONGO_DATABASE=production_db \
  RESTORE_CONFIG=true RESTORE_MINIO=true \
  /opt/myscoutee-template/packaging/scripts/restore-production.sh \
  /var/backups/myscoutee-template/<backup-name>.tar.gz

A failed MongoDB replacement leaves the backend stopped and does not activate the backup encryption key. Ordinary package removal retains deployment data and TLS material. Explicit purge removes this package's state and managed images; external backup archives remain.

Build and sign another release

Use npm --prefix config/packaging run release -- build-production followed by BUILD_ARTIFACTS=false npm --prefix config/packaging run release -- package-production. The existing managed-image policy, install defaults, recovery extension, host checks and release-seed selection own project-specific choices. The template does not install development/test scripts. Do not copy an entire product domain to satisfy a packaging input.

The original pinned MinIO upstream tag became unavailable. An identical amd64 base is preserved at ghcr.io/fssrepository/myscoutee-minio-base, digest sha256:52dfd5c0bbd38d3219f2058c7af216d9f9a27a994b7b5baad09bbd38866015ff. Building from it requires registry access. The five managed images have been published privately and pulled back with matching image IDs. Builds, tests, signing and publication run locally; GitHub Actions is not required. Registry authentication is required for these private images.

prepare-release.py takes an existing private key, the actual DEB and client archive. It signs both, creates matching signed update metadata, verifies signatures and hashes, and records the exact upload set in RELEASE.json. Publish the complete set together; never publish a lone DEB. Private keys belong outside the repository and deployment host. The updater retains strict package/image/version/key checks and durable job state. Keep release assets and their source/image mapping together.

Build Pages locally with MYSCOUTEE_VERSION=1.4.0 npm --prefix frontend run build:github. Commit the generated docs/ directory in the frontend repository. The frontend Pages workflow publishes docs/ after every push to master, and can also be started manually from Actions. In its Pages settings, select GitHub Actions. The build includes .nojekyll; no separate Pages branch is needed. Build, test and signing credentials stay on the development machine.

The GitHub Pages demo uses browser-local data and shows its application version. Live messaging and calls require a backend deployment.
